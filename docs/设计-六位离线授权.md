# 六位离线授权设计

日期：2026-10-17。状态：内部生成端已实现，客户验证端后续接入。按用户要求采用简洁方案，不使用多轮 Agent 评审。实际验证结果单独记录在 `验收记录-六位离线授权.md`。

## 1. 目标与范围

在“DL小工具”新增内部使用的“离线授权”页面：选择客户或设备档案，输入六位申请码，生成六位授权码。现场和生成端均不需要联网，客户不需要收发授权文件。

本次先建设生成端及可复用的计算服务。客户软件的弹窗、验证和授权保存作为后续接入协议说明，不视为本仓库已经实现。当前仓库没有客户软件源码，不修改烧录、打包功能，也不把现有功能改成需要授权才能使用。

首版用途固定为 `ACTIVATE`（激活）；不在六位码中承载有效期、功能组合或多个授权档位，不增加服务器、账号系统或硬件依赖。

## 2. 使用流程与界面

客户软件后续接入时显示：

```text
离线授权
设备：现场设备 A（交付时已分配）
申请码：583194
授权码：[______]
        [确认授权]
```

你的工具显示：

```text
离线授权
客户／设备：[选择档案]
申请码：    [583194]
            [生成授权码]
授权码：     926037    [复制]
```

以上数字仅为界面示例，不是计算向量。客户告诉你申请码及对应设备，你选择档案并计算，再口头或通过既有联系方式告知六位授权码。设备编号可预置在档案内，不要求客户每次手工输入长编号。

输入仅接受六个 ASCII 数字，保留前导零，例如 `000012`；允许去除首尾空白，不接受全角数字、负号、小数或其他字符。修改设备或申请码立即清空旧结果；切换工具页面保留当前输入。复制由用户点击触发，不自动操作剪贴板。

## 3. 计算规则

使用标准 HMAC-SHA256，保密对象是密钥，不依赖隐藏算法。

- 每个档案有独立的 32 字节随机密钥 `K`，由安全随机数生成器创建。
- `DeviceId` 为创建档案时分配的 GUID，固定表示为 32 个大写十六进制字符，无连字符。客户名称只用于展示，不参与计算。
- 首版协议版本固定为 `1`，用途固定为 `ACTIVATE`。
- 消息使用下列固定格式的 ASCII 字节，不含换行：

```text
DLTOOLS-AUTH|1|<DeviceId>|ACTIVATE|<六位申请码>
```

计算 `H = HMAC-SHA256(K, 消息)`。令 `offset = H[31] & 0x0F`，读取 `H[offset..offset+4]` 为大端无符号 32 位整数，清除最高位，取模 `1_000_000`，最后按 `D6` 格式输出。

这是借鉴一次性口令截断方式的自定义挑战应答协议，不宣称是标准 HOTP/TOTP；不依赖双方时钟同步。验证端只比较当前档案、当前申请对应的一个结果，不遍历多个设备、用途或历史申请。

六位码只有一百万种可能，不同请求可能得到相同数字；不能承诺“旧数字在以后绝对不会再次命中”。安全依赖当前请求状态、限次和密钥保护，而非数字永不重复。

### 公开计算示例

以下密钥仅用于开发测试，禁止用于真实客户档案：

```text
K（十六进制字节，不是字符串密钥）：
000102030405060708090A0B0C0D0E0F101112131415161718191A1B1C1D1E1F
DeviceId：11112222333344445555666677778888
```

| 六位申请码 | 截断偏移 | 清除最高位后的整数 | 六位授权码 |
|---|---:|---:|---|
| `000000` | 8 | 367200533 | `200533` |
| `583194` | 0 | 1950677046 | `677046` |
| `999999` | 0 | 304077174 | `077174` |
| `000006` | 14 | 817011864 | `011864` |

例如申请码 `583194` 的完整 HMAC 为 `7444F8363FB5497F5D2527914E74C871AE34CF9B39E341F11B60FAD9725D8900`。上述四组结果已于 2026-10-17 分别使用 .NET 与 Python 标准库复算并一致，覆盖前导零和不同截断位置。这只验证协议计算定义，不代表页面、档案库或客户软件已经实现。

## 4. 档案、密钥与文件保护

档案包括：协议版本、设备标识、显示名称、密钥、创建时间。重命名不能改变设备标识或密钥；更换密钥必须建立新档案并重新配对，不能静默覆盖。

本地保存位置拟为 `%APPDATA%/JLinkRTTViewer/authorization/`，与已有 `packaging/` 子目录分开。Windows 生成端使用当前用户 DPAPI 保护密钥；不将密钥写入源码、普通配置、日志、剪贴板或客户通用程序。DPAPI 不承诺抵抗当前用户权限下的恶意程序，也不能把其密文直接当作跨电脑备份。

提供内部使用的加密备份及恢复：AES-256-GCM，随机 16 字节盐、12 字节 nonce、16 字节 tag；备份密码通过 PBKDF2-HMAC-SHA256（600,000 次）导出 32 字节密钥。文件头记录并校验格式版本和上述固定参数，拒绝未知参数或超大输入，避免不受控的计算与内存消耗。备份使用至少 16 字符的独立强密码，不能使用六位授权码；忘记密码不可恢复。恢复先认证和校验全部档案，再确认冲突并原子保存，失败保留旧库。这些是我方内部备份，客户无需操作。

保存采用跨进程互斥和同目录临时文件原子替换。损坏时保留原文件并提示恢复，不静默生成新密钥。启动先检测可读性，未经成功保存的档案不能生成授权码。日志只记录操作结果，不记录密钥或完整申请码／授权码配对。

## 5. 客户端后续接入约定

生成器本身不能让客户软件自动获得授权能力。双方必须先拥有相同 `DeviceId` 和 `K`，由我方在可信交付或调试环节预置；客户软件不获得其他设备密钥或内部档案库。具体预置载体与接口须在客户项目确定后落实，不把“仅给六位数字”当作首次密钥分发方式。

客户端状态为“未激活 → 等待本次授权 → 已激活”，失败可进入“暂缓尝试”。要求：

1. 用安全随机数生成六位申请码。在同一密钥生命周期内不重复分配已使用的申请码，历史最多一百万个；耗尽后停止新建，走重新配对，不能复用。创建申请时先持久化占用记录，再展示；并发窗口只保留一个当前申请。
2. 关闭弹窗、重启软件后继续使用同一个待处理申请。取消或刷新时旧申请作废，但不能清除累计失败次数。
3. 连续输错逐步延迟，第五次失败后暂停授权尝试 30 分钟；保存失败计数、冷却截止和最近观测时间。检测时间倒退时暂停授权入口并提示校时。仅正常完成冷却或授权成功后重置计数。
4. 输入按六位 ASCII 数字校验，并对等长编码结果进行固定时间比较。每次失败和授权成功都先可靠提交状态，提交失败不能报告成功；重启后不得因旧请求仍在而重复执行业务激活动作。
5. 授权状态与设备标识绑定，使用独立派生的状态保护密钥进行完整性保护；可用 `HMAC-SHA256(K, ASCII("DLTOOLS-STATE|1"))` 派生。软件状态保护可阻止普通修改，但无法阻止有权限者回滚整份历史状态。
6. 授权入口失败不终止正在运行的控制、采集或其他生产任务。实际受控功能在客户项目接入时单独确定。

纯 Windows 实现只能定位为防误用、防普通试码。调试提取密钥、修改验证代码、虚拟机快照及删除／回滚本地状态，均超出该等级保证；代码混淆不能消除此边界。若要求可靠抵抗这些攻击，需要由受保护硬件保存密钥和状态，再单独实施。

重装电脑可能同时丢失本地授权、申请历史以及密钥。若交付机制能重新预置同一设备密钥，可以重新申请并由你回复六位码；若密钥也无法恢复，必须先重新配对，不能承诺单凭六位码恢复。完全离线的纯软件方案不承诺重装后自动保留授权。

## 6. 项目内修改位置与实施顺序

当前项目为 .NET 8 Windows x64 WPF，`MainWindowViewModel` 缓存烧录和打包页面，页面继承 `BasePage`，使用 CommunityToolkit.Mvvm。按现有组织方式新增，不搬迁源码或改变命名空间。

| 步骤 | 预计修改位置 | 内容与完成条件 |
|---|---|---|
| 1. 计算核心 | `Models/Authorization/`、`Services/Authorization/OfflineAuthorizationService.cs` | 定义档案及协议；实现纯计算服务；固定向量、前导零和非法输入测试通过 |
| 2. 档案存储 | `Services/Authorization/AuthorizationProfileStore.cs`、`AuthorizationBackupService.cs` | 新建、重命名、加密保存、备份恢复；断电式失败、密码错误、文件损坏和并发测试证明旧数据受保护 |
| 3. 页面接入 | `Pages/OfflineAuthorizationPage.xaml` 及代码文件、`ViewModels/OfflineAuthorizationViewModel.cs`、`MainWindow.xaml`、`MainWindowViewModel.cs` | 增加“离线授权”导航；可选择档案、输入、生成、复制，切页保留状态 |
| 4. 验证交付 | `tests/DLTools.Tests/OfflineAuthorizationTests.cs` 等、README | 离线端到端演示、异常测试及现有功能回归通过，明确客户验证端尚待接入 |

步骤依次进行，每步通过针对性测试后再进入下一步。耗时的存储／备份任务登记 `BackgroundTaskHost`，新增 `Authorization` 操作类型并调整关闭提示；沿用任务结束后释放资格的规则。用户取消备份／恢复不留下部分替换的档案库。六位码计算本身不启动外部进程。

## 7. 验收与安全边界

- 断网时，选择档案并输入六位申请码，稳定生成六位结果；同一密钥和请求两端得到相同结果。
- 使用公开测试密钥冻结跨实现向量；覆盖 `000000`、`999999`、前导零、Unicode 数字、非法长度、字节序及截断偏移。不同设备结果可能偶然碰撞，不能将“永不相等”写成测试断言。
- 档案不存在、库损坏、备份密码错误、恢复冲突或存储失败时，显示明确原因且不丢失原档案；密钥和响应码不进入日志。
- 在无 J-Link 环境启动并使用生成器；切页、最小窗口及忙碌关窗遵循已有规则，烧录和打包不被授权逻辑拦截。
- 客户端接入后另测限次、刷新、重启、断电、时间回拨、重放及授权保存；尚未接入的客户端和硬件测试不得记录为通过。

常规检查：`dotnet build "DL小工具.sln" -c Release`，以及 `dotnet test "tests/DLTools.Tests/DLTools.Tests.csproj" -c Release`。本次实现内部生成端及档案管理；客户验证端仍按第5节另行接入，限次和授权保存不能仅由本仓库生成器保证。

参考：[RFC 4226：截断、限次与密钥管理](https://www.rfc-editor.org/rfc/rfc4226.html)、[.NET 安全随机整数](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.randomnumbergenerator.getint32?view=net-8.0)、[OWASP 密码派生建议](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。此设计不是标准认证协议合规声明。
